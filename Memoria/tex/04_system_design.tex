\chapter{System Design}\label{ch:design}

This chapter describes how the concepts introduced in Chapter~\ref{ch:sota} are instantiated into
a concrete software architecture. Section~\ref{sec:design-architecture} presents the layered
wrapper chain, Sections~\ref{sec:design-obs}--\ref{sec:design-action} formalise the observation
and action spaces, Section~\ref{sec:design-agent} describes the PPO agent,
Section~\ref{sec:design-shields} the two safety shields,
Section~\ref{sec:design-reward} the reward shaper, Section~\ref{sec:design-curriculum} the
curriculum manager and Section~\ref{sec:design-metrics} the live metrics pipeline.

\section{Architectural overview}\label{sec:design-architecture}

The framework is organised as a vertical stack of components that communicate through the
standard \texttt{gymnasium.Env} interface. Each layer consumes the observation produced by the
layer below and may transform both the action travelling downwards and the reward travelling
upwards. Figure~\ref{fig:wrapper-chain} shows the chain.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.75\textwidth]{imgs/wrapper_chain}
  \caption{Wrapper chain of the framework. Each layer is a \texttt{gymnasium.Wrapper} that can be
           composed, replaced or removed without touching its neighbours. The safety shield sits
           above the reward shaper so that shield diagnostics (\texttt{executed\_action},
           \texttt{risk\_level}) are available to the shaper when it computes the intervention
           penalty.}
  \label{fig:wrapper-chain}
\end{figure}

A subtlety of this layout deserves comment. The reward shaper is placed \emph{above} the shield
(outermost wrapper, closest to the agent), not below it. The shield is the \emph{inner} wrapper,
between the shaper and \texttt{CarlaEnv}. This ordering has a functional reason: when the shaper
calls \texttt{self.env.step(action)}, the inner shield runs first and enriches the returned
\texttt{info} dictionary with the keys \texttt{executed\_action} and \texttt{proposed\_action};
the shaper can then read those keys to compute the shield-intervention penalty and the smoothness
penalty. If the shaper were placed \emph{below} (inner to) the shield, those keys would not yet
exist when the shaper processes its call.

The environment runs in \emph{synchronous mode} with a fixed time step of \(\Delta t =
0.05\,\mathrm{s}\). Every call to \texttt{env.step(action)} sends the action to CARLA, requests
a single \texttt{world.tick()} and collects the resulting sensor readings. This guarantees
determinism given a fixed seed.

\section{Observation space}\label{sec:design-obs}

The observation vector \(s_t \in \mathbb{R}^{739}\) concatenates three semantic LIDAR channels
and a 19-dimensional block of geometric and route features. Appendix~\ref{app:observation}
contains the full index-by-index table; this section describes the design rationale.

\subsection{Semantic LIDAR}\label{sec:design-obs-lidar}

The framework uses a simulated LIDAR with \(N = 240\) rays uniformly distributed over
\(360^\circ\) (angular resolution \(1.5^\circ/\text{ray}\), range \(50\,\mathrm{m}\)). Each
ray is normalised to \([0, 1]\), where \(1\) denotes a free ray and values near \(0\) denote
an obstacle close to the vehicle. The semantic channel is obtained from CARLA's
\texttt{SemanticLidarSensor}, which tags every ray hit with the
\texttt{carla.CityObjectLabel} of the struck primitive.

Three derived channels are packed into the observation (see Figure~\ref{fig:lidar-channels}):

\begin{itemize}
  \item \(\text{obs}[0{:}240]\), \textbf{combined channel}: all obstacles
        (dynamic and static) plus road edges.
  \item \(\text{obs}[240{:}480]\), \textbf{dynamic-only channel}: vehicles and
        pedestrians only.
  \item \(\text{obs}[480{:}720]\), \textbf{static-only channel}: walls, barriers,
        poles and similar static objects.
\end{itemize}

\begin{figure}[H]
  \centering
  \includegraphics[width=0.9\textwidth]{imgs/lidar_channels}
  \caption{The three semantic LIDAR channels. Combined (left) includes all obstacles; dynamic
           (centre) keeps only vehicles and pedestrians; static (right) keeps only walls and
           barriers. Coloured sectors mark the angular regions used by the shields: front
           (\(\pm22.5^\circ\), rays 225--240 and 0--15) in red, right side (\(60^\circ\)--\(120^\circ\))
           and left side (\(240^\circ\)--\(300^\circ\)) in blue.}
  \label{fig:lidar-channels}
\end{figure}

The channel decomposition is motivated by an empirical observation: a single-channel LIDAR
induces a \emph{zig-zag} pattern when driving along a guardrail, because the policy interprets
static low-range returns as moving obstacles and tries to evade laterally. Separating dynamic
from static obstacles allows the policy to treat static boundaries as soft lane edges while
properly anticipating dynamic hazards.

\subsection{Lane, marking, vehicle and route features}\label{sec:design-obs-vector}

A 19-dimensional vector block is appended to the LIDAR. Its components are:

\begin{itemize}
  \item \(\text{obs}[720{:}728]\), \textbf{lane features (8 dims)}: lateral offset,
        heading error, edge warning, lane width, left/right edge distances, lane-change
        permission, road curvature.
  \item \(\text{obs}[728{:}732]\), \textbf{lane-marking type (4 dims)}: binary flags
        for solid-left, solid-right, dashed-left, dashed-right. These allow the policy to
        distinguish legal lane changes (dashed) from illegal solid-line crossings.
  \item \(\text{obs}[732{:}734]\), \textbf{vehicle state (2 dims)}: normalised speed,
        last applied steering.
  \item \(\text{obs}[734{:}739]\), \textbf{route features (5 dims)}: waypoint angle
        at 5\,m, waypoint angle at 20\,m, progress fraction, normalised speed limit, speed
        ratio.
\end{itemize}

All features are extracted from CARLA's Waypoint API. The lateral edge distances are normalised
by the lane width so that both take the value \(0.5\) at the lane centre and approach \(0\) at
the corresponding edge. The LIDAR block (\(\text{obs}[0{:}720]\)) is clipped to \([0,1]\); the
vector block (\(\text{obs}[720{:}739]\)) is clipped to \([-1,1]\).

\section{Action space}\label{sec:design-action}

The action space is \(\mathcal{A} = [-1, 1]^2\). Its two components are:
\begin{itemize}
  \item \(a^{(1)}\), \emph{steering}, mapped linearly to physical steering
        \(\delta \in [-0.6,\, +0.6]\,\mathrm{rad}\).
  \item \(a^{(2)}\), \emph{joint throttle\textendash brake}: positive values drive
        the throttle (up to \(+3.0\,\mathrm{m/s^2}\)), negative values drive the brake (up to
        \(-7.0\,\mathrm{m/s^2}\)), zero is coast.
\end{itemize}

Merging throttle and brake into a single signed channel reduces the output dimensionality and
prevents the agent from learning the counter-productive behaviour of applying both simultaneously.

Continuous actions are sampled from a diagonal Gaussian and squashed through a hyperbolic
tangent to keep them inside the box:
\begin{equation}
  u_t \sim \mathcal{N}\!\big(\mu_\theta(s_t),\, \sigma_\theta^2\big),
  \qquad
  a_t = \tanh(u_t).
  \label{eq:policy-squash}
\end{equation}
Computing the log probability of a squashed sample requires adding the log-determinant of the
tanh Jacobian~\cite{haarnoja2018sac}, a correction that is also applied when evaluating the
log probability of an executed (possibly shield-modified) action for credit assignment.

\section{Agent design}\label{sec:design-agent}

\subsection{Actor\textendash Critic network}\label{sec:design-agent-net}

The actor and the critic share a representation but have separate heads
(Figure~\ref{fig:actor-critic-arch}). Feeding the raw 739-dimensional observation directly
into a shallow MLP dilutes the signal: the 720 LIDAR dimensions dominate numerically while the
19 lane/vehicle/route features carry most task-relevant information. The network therefore
includes a dedicated \emph{LIDAR encoder}: a two-layer MLP with 256 hidden units that
compresses the 720-dimensional LIDAR input to a 64-dimensional representation. This 64-dim
summary is concatenated with the 19-dimensional vector block to produce an 83-dimensional
feature \(\phi(s_t)\) that feeds the actor and critic trunks.

Both actor and critic trunks are two-layer MLPs with 256 units per hidden layer and Tanh
activations. The actor head produces a 2-dimensional mean \(\mu_\theta(s_t)\) together with a
state-independent log-standard-deviation parameter. The log-std is bounded to the range
\([-3.0,\, -1.2]\) (corresponding to \(\sigma \in [0.05, 0.30]\)) via a tanh-squashed
parameterization so that the effective \(\sigma\) can \emph{anneal down} as the policy
converges. The effective initial log-std is \(-1.5\) (\(\sigma \approx 0.22\)). The critic head
produces a scalar value estimate \(V_\theta(s_t)\).

\begin{figure}[H]
  \centering
  \includegraphics[width=0.95\textwidth]{imgs/actor_critic_arch}
  \caption{Actor-Critic architecture. The LIDAR encoder compresses 720 LIDAR dimensions to 64;
           the resulting 83-dimensional feature feeds two independent trunks. The actor outputs a
           2D mean and a state-independent log-std (bounded via tanh squashing to
           \([-3.0,\,-1.2]\)); the critic outputs a scalar value estimate \(V_\theta(s_t)\).}
  \label{fig:actor-critic-arch}
\end{figure}

\subsection{PPO update}\label{sec:design-agent-ppo}

At each environment step the agent appends the tuple
\(\bigl(s_t,\, a^\star_t,\, \log \pi_\theta(a^\star_t\mid s_t),\, r_t,\, d_t,\, \mathrm{trunc}_t,\, V^{\text{boot}}_t\bigr)\)
to the rollout buffer. Two details are specific to this project:

\begin{enumerate}
  \item The buffer stores the \emph{executed} action \(a^\star_t\), not the sampled action. The
        stored log probability is recomputed by \texttt{evaluate\_action} using the log-det
        Jacobian correction of Equation~\eqref{eq:policy-squash}. This ties the gradient
        computation to the action the environment actually saw, avoiding the credit-assignment
        error that would otherwise be introduced by the shield.
  \item When an episode is truncated by a timeout, the critic value \(V_\theta(s_{T+1})\)
        is stored as \(V^{\text{boot}}_t\) and used to bootstrap GAE at that step. For natural
        terminations (collision, off-road), \(V^{\text{boot}}_t = 0\).
\end{enumerate}

When the buffer reaches \(M = 2048\) samples, GAE (Equation~\eqref{eq:gae}) is run backwards
through the rollout, advantages are standardised, and the return target is divided by a running
standard deviation (Section~\ref{sec:design-returnnorm}). Up to \(K = 10\) epochs of PPO are
then performed with SB3-style minibatching (minibatch size 64, giving 32 Adam steps per epoch),
with a KL early stop governed by the mechanism of Section~\ref{sec:sota-ppo-stabilisers}. The
gradient is clipped to an \(\ell_2\) norm of \(0.5\) and the learning rate follows a cosine
annealing schedule.

\subsection{Observation normalisation}\label{sec:design-obsnorm}

Online normalisation is performed on the 19-dimensional vector block only, using Welford's
incremental mean/variance estimator~\cite{welford1962notes}. The estimator maintains a running
mean \(\hat{\mu}\) and variance \(\hat{\sigma}^2\) that are updated in mini-batches and used to
rescale each feature to approximately zero mean and unit variance. Normalised observations are
clipped to \([-5, 5]\) to contain outliers.

The 720 LIDAR dimensions are left un-normalised because they are already in \([0,1]\) by
construction. Applying normalisation would artificially introduce distribution shift when the
curriculum advances from stage~0 (no NPCs, constant-1.0 dynamic channel) to stage~1 (dynamic
channel suddenly has non-unit entries), causing the gradient spikes observed in early prototypes.

\subsection{Return normalisation}\label{sec:design-returnnorm}

The return targets passed to the critic loss can span several orders of magnitude as the agent
learns, which makes MSE training unstable. To counter this, returns are divided by the running
standard deviation of a discounted-return accumulator that is updated across rollout boundaries.
The mean is deliberately \emph{not} subtracted, as subtracting a running mean would bias the
advantages (which are already standardised separately).

\section{Safety shields}\label{sec:design-shields}

Both shields implement the function \(\Sigma\) of Equation~\eqref{eq:shield-fn}. They differ in
the information they consume and the strategy by which they generate the corrected action.

\subsection{Basic shield}\label{sec:design-basic-shield}

The basic shield (\texttt{CarlaSafetyShield}) operates in two layers. The first analyses the
combined LIDAR scan for imminent obstacles by comparing minimum values in three angular sectors
(front: \(\pm22.5^\circ\), right side: \(60^\circ\)--\(120^\circ\), left side:
\(240^\circ\)--\(300^\circ\)) against fixed thresholds (\(\tau_f = 0.15\) for the front,
\(\tau_s = 0.04\) for the sides). The front sector spans rays \([225{:}240] \cup [0{:}15]\)
(30 of the 240 rays at \(1.5^\circ/\text{ray}\)). The second layer reads the lateral offset
and heading error from the \texttt{info} dictionary and flags the situation as unsafe when they
exceed their respective thresholds (\(\tau_\ell = 0.82\), \(\tau_h = 0.60\)).

When the situation is unsafe, the shield applies a proportional correction: the steering command
is adjusted to push the vehicle back towards the lane centre (combining lateral offset, heading
error and any required lateral obstacle push), and a braking command is applied proportionally
to the detected frontal clearance deficit. Both corrections are clipped to the action range and
combine the \emph{minimal-interference principle}: when all threats are far from their thresholds
the corrections vanish and the shield passes the agent's action through unmodified.

\subsection{Adaptive-horizon shield}\label{sec:design-adaptive-shield}

The adaptive-horizon shield (\texttt{CarlaAdaptiveHorizonShield}) extends the basic design with
three mechanisms: a risk classifier, trajectory prediction with the bicycle model, and a
priority-ordered candidate search.

\paragraph{Risk classifier.}
Two independent criteria jointly determine the risk level (Figure~\ref{fig:risk-levels}). The
\emph{frontal-distance criterion} thresholds the minimum of the dynamic-only LIDAR front sector:
\begin{equation}
  \mathrm{level}^{\mathrm{frontal}}_t \;=\;
     \begin{cases}
       \mathrm{safe}     & \text{if } d^{\mathrm{dyn}}_t > 0.50,\\
       \mathrm{warning}  & \text{if } 0.20 < d^{\mathrm{dyn}}_t \le 0.50,\\
       \mathrm{critical} & \text{if } d^{\mathrm{dyn}}_t \le 0.20.
     \end{cases}
  \label{eq:shield-risk-front}
\end{equation}
The \emph{lateral-position criterion} thresholds \(|\ell_t|\) at \(0.50\) (warning) and
\(0.70\) (critical), and the absolute heading error \(|\psi_t|\) at \(10^\circ\) (warning) and
\(20^\circ\) (critical). The overall level is the worst of the two criteria.

Each risk level fixes a trajectory-prediction horizon \(H\) and a threshold multiplier
\(\kappa\): \(\mathrm{safe}\): \(H=1\), \(\kappa=1.0\); \(\mathrm{warning}\): \(H=5\),
\(\kappa=1.5\); \(\mathrm{critical}\): \(H=10\), \(\kappa=2.0\).

\begin{figure}[H]
  \centering
  \includegraphics[width=0.85\textwidth]{imgs/risk_levels}
  \caption{Risk level classification of the adaptive shield. Each step is independently assessed
           by a frontal-distance criterion (rows, thresholds at 0.50 and 0.20) and a
           lateral-position criterion (columns, thresholds at \(|\ell|=0.50\)/\(0.70\) and
           \(|\psi|=10^\circ\)/\(20^\circ\)); the overall level is the worst of both. The
           corresponding trajectory-prediction horizon \(H\) and threshold multiplier \(\kappa\)
           are shown in each cell.}
  \label{fig:risk-levels}
\end{figure}

\paragraph{Trajectory check.}
Given a candidate action, the shield asks the bicycle model of Section~\ref{sec:sota-bicycle}
for the trajectory over \(H\) steps. Each predicted position is projected onto the nearest
driving lane via CARLA's Waypoint API. The candidate is declared safe when all of the following
hold simultaneously:
\begin{itemize}
  \item The combined front LIDAR minimum exceeds \(\tau_f / \kappa\).
  \item Static side LIDAR minima exceed \(\tau_s / \kappa\) (unless the ego is safely centred
        in lane with both edge distances above \(0.3\)).
  \item The nearest edge distance exceeds the hard floor \(0.15\).
  \item The nearest pedestrian is more than \(4.0\,\mathrm{m}\) away.
  \item Every predicted lateral offset along the trajectory satisfies
        \(|\ell_k| / (w_{\mathrm{lane}}/2) \le \tau_\ell^{\mathrm{level}}\), where
        \(\tau_\ell^{\mathrm{level}} \in \{0.55,\, 0.40,\, 0.30\}\) for
        \(\{\text{safe},\,\text{warning},\,\text{critical}\}\) respectively.
  \item No predicted heading deviates more than \(0.52/\kappa\,\mathrm{rad}\) from the
        nearest lane direction, and no predicted lateral drift exceeds \(1.75/\kappa\,\mathrm{m}\)
        from the reference position.
\end{itemize}

\paragraph{Minimal-interference projection.}
If the proposed action fails the trajectory check, the shield computes an \emph{emergency action}
\(a^{\mathrm{em}}_t\) whose steering corrects the lateral offset and heading error and whose
throttle/brake depends on the severity of the threat. It then searches the first mixing coefficient
\(\alpha \in \{0.25,\, 0.50,\, 0.75,\, 1.0\}\) such that the blended action
\begin{equation}
  a_t(\alpha) \;=\; (1-\alpha)\,a^{\mathrm{prop}}_t \;+\; \alpha\,a^{\mathrm{em}}_t
  \label{eq:alpha-blend}
\end{equation}
passes the trajectory check. The first safe blend is executed; if none passes,
\(a^{\mathrm{em}}_t\) is executed with \(\alpha = 1\). This \emph{minimal-interference
projection} keeps the executed action close to the agent's proposal (small corrections use
\(\alpha = 0.25\)) and avoids the numerical instability of hard-coded fallback vectors that
would saturate the tanh policy output.

\paragraph{Pedestrian emergency.}
If the nearest pedestrian is detected at less than \(4\,\mathrm{m}\), the shield bypasses the
projection and issues a full brake \(a_t = (0,\, -1)\) with \(\alpha = 1\).

\section{Reward shaping}\label{sec:design-reward}

The reward shaper \texttt{CarlaRewardShaper} augments the sparse base reward \(r^{\mathrm{base}}_t\)
of \texttt{CarlaEnv} (success \(+30\), collision \(-10\), off-road \(-30\)) with dense components
that provide continuous feedback during the episode. Figure~\ref{fig:reward-overview} gives an
overview; the total shaped reward is
\begin{equation}
  \tilde{r}_t \;=\; r^{\mathrm{base}}_t
    + r^{\mathrm{prog}}_t + r^{\mathrm{accel}}_t + r^{\mathrm{speed}}_t
    + r^{\mathrm{lane}}_t + r^{\mathrm{head}}_t + r^{\mathrm{mile}}_t
    - p^{\mathrm{smooth}}_t - p^{\mathrm{inv}}_t - p^{\mathrm{solid}}_t
    - p^{\mathrm{edge}}_t - p^{\mathrm{wrong\text{-}h}}_t
    - p^{\mathrm{idle}}_t - p^{\mathrm{drift}}_t
    - p^{\mathrm{lc}}_t - p^{\mathrm{shield}}_t.
  \label{eq:shaped-reward}
\end{equation}

\begin{figure}[H]
  \centering
  \includegraphics[width=0.9\textwidth]{imgs/reward_overview}
  \caption{Overview of the dense reward components plus the sparse base reward. Bonuses
           (green) reward forward progress, speed compliance and lane discipline; penalties
           (red) penalise unsafe driving, stalling and unnecessary shield activations.}
  \label{fig:reward-overview}
\end{figure}

The dense bonuses \(r^{\mathrm{prog}}_t\), \(r^{\mathrm{accel}}_t\) and the positive part of
\(r^{\mathrm{speed}}_t\) are multiplied by a \emph{lane-keep gate}
\(\mu_t \in [0,\,1]\) that rewards forward progress only when the vehicle is correctly positioned
in the lane:
\begin{equation}
  \mu_t \;=\;
  \underbrace{\max(1 - |\ell_t|,\, 0)}_{\text{centering factor}}
  \;\times\;
  \underbrace{\max\!\left(1 - \frac{|\psi_t|}{20^\circ},\, 0\right)}_{\text{heading factor}},
  \label{eq:lane-keep-gate}
\end{equation}
where \(\ell_t\) is the normalised lateral offset and \(\psi_t\) is the heading error in degrees.
During a permitted lane-change manoeuvre (\(\ell_t > 0.5\) and CARLA reports lane change
allowed), \(\mu_t\) is floored at \(0.3\) so that the agent is not penalised for intentionally
crossing the lane centre.

The individual components are described below. Default weights are in
Appendix~\ref{app:hyperparameters}, Table~\ref{tab:hp-reward}.

\paragraph{Progress reward \(r^{\mathrm{prog}}_t\).}
A continuous speed-proportional bonus \(r^{\mathrm{prog}}_t = \mathrm{clip}(v_t /
10\,\mathrm{km/h},\,0,\,1) \times w_{\mathrm{prog}} \times \mu_t\), active only when on-road.
Saturation at \(10\,\mathrm{km/h}\) avoids rewarding excessive speed purely for progress, while
the lane-keep gate \(\mu_t\) closes the local optimum of driving fast while off-lane.

\paragraph{Acceleration reward \(r^{\mathrm{accel}}_t\).}
\(r^{\mathrm{accel}}_t = \mathrm{clip}(\Delta v_t,\,0,\,2\,\mathrm{km/h}) \times
w_{\mathrm{accel}} \times \mu_t\). Provides a dense positive signal from the very first
acceleration step (before the vehicle reaches any speed threshold), encouraging the agent to
start moving instead of stalling.

\paragraph{Speed bonus.}
A Gaussian bonus centred on a curvature-adjusted target speed: the target is reduced in sharp
bends to discourage excessive speed around turns. An over-speed penalty applies when the vehicle
exceeds the raw speed limit by more than 5\%.

\paragraph{Lane centring and heading alignment.}
\(r^{\mathrm{lane}}_t = \max(1 - |\ell_t|,\,0) \times w_{\mathrm{lc}}\) and
\(r^{\mathrm{head}}_t = \max(1 - |\psi_t|/20^\circ,\,0) \times w_{\mathrm{h}}\),
both gated by a recent-movement flag (suppressed if the vehicle has been stationary for
\(\ge 5\) consecutive steps) so the agent is not rewarded for parking precisely in lane.

\paragraph{Smoothness penalty.}
Proportional to the absolute steering change between successive steps. This penalises erratic
inputs and encourages smooth driving.

\paragraph{Lane-invasion penalty.}
A flat penalty of \(-2.5\) per solid-line crossing, capped at 6 events per episode (hard cap
\(-15\)). The flat structure replaces the earlier geometric decay that diluted marginal cost so
rapidly that an off-lane agent had no gradient to return. Raw event count is still exposed in
\texttt{info["solid\_invasion\_event"]}.

\paragraph{Edge proximity, wrong-heading and drift penalties.}
\(p^{\mathrm{edge}}_t = 0.6 \times \max(0,\, 0.5 - \min(\ell^L_t, \ell^R_t))\), where
\(\ell^{L,R}_t\) are the normalised left/right edge distances; the threshold is \(0.5\), not
\(0.4\). A penalty for heading error exceeding \(90^\circ\), and a drift penalty for asymmetric
edge distances when the vehicle is hugging one side.

\paragraph{Solid-line invasion.}
A flat penalty \(-p_{\mathrm{solid}} = -2.5\) per solid-lane-marking crossing, capped at
\(N_{\mathrm{cap}} = 6\) events per episode (maximum accumulation \(-15\)).  The flat structure
preserves a constant marginal cost for every crossing, which a geometric decay design had
diluted to near zero after the first two or three events, eliminating the return gradient for an
agent already committed off-lane.

\paragraph{Lane-change cost.}
A small cost \(-0.05\) per detected lane-change event (cooldown 20 steps), discouraging
gratuitous lane-switching.

\paragraph{Shield-reliance penalty.}
An optional penalty \(p^{\mathrm{shield}}_t = w_{\mathrm{sh}} \times \alpha_t\) proportional to
the shield intensity \(\alpha_t \in [0,1]\). Default weight is \(0\); can be set positive to
make reliance reward-sub-optimal. Suppressed during a permitted lane-change transition.

\paragraph{Progress bonus.}
A fixed bonus every time the vehicle crosses a \(25\,\mathrm{m}\) milestone along the route. This
prevents a pure speed bonus from rewarding high speed regardless of whether the vehicle is
actually advancing along the intended route.

% Shield interaction is now covered by the "Shield-reliance penalty" paragraph above.

\paragraph{Idle penalty and shield grace period.}
An idle penalty discourages the agent from stopping. To prevent this from punishing legitimate
shield-induced stalls (e.g.\ the anti-deadlock recovery of Section~\ref{sec:design-shields}), a
grace period of \(G = 10\) steps is opened the first time the shield activates in an episode.
The counter is re-armed only when the shield fires and the grace period has already expired,
preventing an always-active shield from permanently suppressing the idle penalty.

\paragraph{Lane-change transition guard.}
When CARLA's Waypoint API reports that a lane change is permitted and the lateral offset exceeds
\(0.5\), the invasion, edge and drift penalties are all set to zero. This prevents the agent from
being penalised for a legitimate lane-change manoeuvre during training.

\section{Curriculum manager}\label{sec:design-curriculum}

The curriculum manager divides the NPC interval \([0,\, N_{\max}]\) uniformly into five stages.
For the default \(N_{\max}=40\) this yields \((0,\,10,\,20,\,30,\,40)\). It maintains two
counters: the episode count at the current stage \(E_{\mathrm{stage}}\) and a decay-weighted
rollback counter \(C_{\mathrm{rb}}\). Figure~\ref{fig:curriculum-stages} illustrates the state
machine.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.9\textwidth]{imgs/curriculum_stages}
  \caption{Curriculum state machine. Forward arrows show the performance threshold required to
           advance (evaluated after at least 100 episodes at the current stage). Backward arrows
           show rollback, triggered when a decay-weighted counter reaches 50 consecutive collapse
           episodes.}
  \label{fig:curriculum-stages}
\end{figure}

\paragraph{Advancement rule.}
After \(E_{\mathrm{stage}} \ge 100\) episodes, if the stage-specific condition in
Table~\ref{tab:curriculum-rules} is met, the manager advances one stage and resets all counters.

\paragraph{Rollback rule.}
On every episode beyond the minimum, \(C_{\mathrm{rb}}\) is incremented by one if the stage is
\emph{collapsing} and decremented by one otherwise (but not below zero). When
\(C_{\mathrm{rb}} \ge 50\), the manager rolls back one stage. The decay by \(-1\) on
non-collapsing episodes prevents a streak of bad luck from triggering a rollback that is not
warranted by a sustained performance drop.

\begin{table}[H]
  \centering
  \caption{Advancement and rollback thresholds per curriculum stage. All rates are 100-episode

\paragraph{Non-disruptive NPC update.}
When the stage changes, the manager updates \texttt{CarlaEnv.num\_npc\_vehicles} in place; the
change takes effect at the next \texttt{env.reset()}, avoiding the deadlock observed in earlier
prototypes that rebuilt the wrapper chain on every stage change.

\section{Live metrics pipeline}\label{sec:design-metrics}

Training metrics are written to a per-run SQLite database at
\texttt{runs/\textless run\_name\textgreater/metrics.sqlite}. The logger
(\texttt{src/Metrics/live\_metrics.py}) opens the database in \emph{Write-Ahead Logging} (WAL)
mode~\cite{sqlitewal}, which allows concurrent reads and writes: the training process writes while
the Streamlit dashboard reads in real time.

Two tables are used:
\begin{itemize}
  \item \texttt{metrics\_episode}: one row per episode. Columns include reward components, safety
        rates, curriculum stage and LIDAR-derived minimum distances.
  \item \texttt{metrics\_update}: one row per PPO update. Columns include policy loss, value loss,
        approximate KL, epochs run, gradient norm and current learning rate.
\end{itemize}

The dashboard (\texttt{dataVisualizer.py}) reads both tables every few seconds and renders
interactive Plotly charts. Unknown metric keys are rendered as soft-typed line plots, keeping
the dashboard forward-compatible with future additions to the logger.
